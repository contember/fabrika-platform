# Cloudflare D1

## What it is

SQLite-at-the-edge: the relational store for an app's **mutable, human-driven
state**. Bound as `env.DB` and queried inside the Worker (request/RPC handlers,
services, queue or scheduled handlers). SSR loaders/actions are one possible
transport; a Buzola SPA reaches D1 only through the Worker API. Migrations are
SQL files; local D1 lives under `.lopata/` (lopata) or `--local` (wrangler).

## When & why to use

- Default store for relational/mutable state (users, projects, config, issues…).
- You want SQL + local-first dev with no account.

## When NOT to use

- **High-frequency append/counter workload** (per-event count UPDATE = hot-row contention) → use `analytics-engine` behind `count-store`, append don't UPDATE.
- Coordination / strong single-object consistency → `durable-objects`.
- Large binary payloads → `r2`.

## Impacts & gotchas

- **Migrations are idempotent**: `migrations/NNNN_name.sql`, `CREATE TABLE IF NOT EXISTS`. Dir = oblaka `migrationsDir`.
- Keep D1 behind the Worker boundary. Inject `env.DB` into handlers/services;
  never import a Worker binding into client SPA code.
- Apply: `lopata d1 migrations apply` (local-first) or `wrangler d1 migrations apply DB --local`.

## Relationships — why

- **requires `cloudflare`** — it's a CF binding.
- **recommends `oblaka`** — declare the `D1Database` binding in `oblaka.ts` rather than hand-editing `wrangler.jsonc`.
- **conflicts `postgres`** — same `relational-db` slot (edge SQLite vs a Postgres server). A `contember` stack uses Postgres, not D1.
