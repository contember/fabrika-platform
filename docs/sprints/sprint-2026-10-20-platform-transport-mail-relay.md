# Sprint — the platform transport and the gated mail relay (2026-10-20)

**Goal.** An application on framework 0.6 sends installation mail to Control over a platform transport, and Control
records, gates and dispatches it; IAM on Zerops sends through the same relay, always passed.

**Theme.** The idea that specified this sprint graduated into [ADR-0064](../decisions/0064-applications-reach-the-platform-over-a-receiver-verified-transport-key.md) (the platform transport) and [ADR-0019](../decisions/0019-portable-outbound-email.md) §8 (the relay). Zerops only.
Base: `feat/declare-the-surface` (framework 0.6.0). The success condition: a 0.6 application's job sends a mail, the
relay holds it under a `hold` rule, an operator releases it in the console, the provider (the local stack's
`directory`) receives it; a 0.5 application on the same Control still gets the direct credential and sends as before.

## Binding rules for every WU

- ADR-0062: everything is additive on the platform side. A 0.4 or 0.5 application, and a 0.6 snapshot without
  `framework`, keeps today's `FABRIKA_EMAIL_*` with the provider credential.
- No `as`, `any`, `@ts-ignore`, `@ts-expect-error`. Parse at boundaries (the relay's request body, stored rows).
- Never log a key, a mail body, a subject or a recipient. A log line is a fixed code plus ids.
- Control's SQL rules: `packages/control/DATABASE.md` (both dialects state the same outcome, callers pass `now()`).
- Generate ids caller-side (UUIDv7).

## Design (frozen)

### Variables (auth-core)

- New framework family `FABRIKA_PLATFORM_`. `platformTransportVariables('mail')` →
  `{ url: 'FABRIKA_PLATFORM_MAIL_URL', key: 'FABRIKA_PLATFORM_MAIL_KEY' }`. `PLATFORM_RECEIVERS = ['mail']`.
- The URL is public (not scrubbed); the key is secret. `FABRIKA_EMAIL_PROVIDER` joins the scrubber's public list,
  because `platform` is eight characters.
- Zerops: the URL is a service-level plain variable, the key sensitive. Cloudflare refuses the family, as it refuses
  `FABRIKA_EMAIL_*`.

### Wire (`@fabrika/email/platform`)

- `POST <url>/platform/mail/send`, `Authorization: Bearer <key>`, `Content-Type: application/json`.
- Body: the `EmailMessage` fields; attachments as `{ filename, contentType, contentBase64 }`. Parsed with one parser
  on the relay side (`parsePlatformMailRequest`) that ends in the package's own message validation.
- Answer: `200 { status: 'accepted', messageId }`, or `{ error: { code } }` with an `EmailDeliveryErrorCode`, so the
  relay's `retryable` and `outcome` reach the caller unchanged. Status: 400 `invalid_message`, 401
  `provider_unauthorized`, 409 `idempotency_conflict`, 503 `provider_unavailable`.
- `PLATFORM_MAIL_CAPABILITIES`: `idempotent: true`, `confirmation: 'queued'`, `maxBatch: 1`,
  `listUnsubscribe: true`, `maxAttachmentBytes: 10 MiB`.
- `PlatformEmailSender({ url, key, fetch?, timeoutMs? })` implements `EmailSender` and passes the conformance kit.

### Application side (`@fabrika/app`)

- `FABRIKA_EMAIL_PROVIDER=platform` makes `ctx.mail` build a `PlatformEmailSender` from
  `FABRIKA_PLATFORM_MAIL_URL/_KEY`, not through the provider registry. No `FABRIKA_EMAIL_FROM` is needed with it. A
  missing URL or key refuses the boot (`invalid_configuration`). `mailKeyPrefix` stays.

### Control: keys

- One key per `<app>@<env>` and receiver, `px_` + 160 random bits, generated by Control. Stored: the SHA-256 hash in
  `platform_transport_keys`, the value sealed in the vault (`platform:platform-key:<app>@<env>:mail`). Rotated when
  less than half of its 30-day life is left; the old hash stays valid until its own expiry.
- A deploy of an environment that has a `mailer: 'installation'` job, on Zerops (the namespace-proxy path), whose
  approved snapshot's `framework` is `>= 0.6.0`, hands `FABRIKA_EMAIL_PROVIDER=platform`,
  `FABRIKA_PLATFORM_MAIL_URL` (Control's private origin, `http://control:3000` on Zerops) and the key, and nothing of
  the provider. Every other case keeps `installationMailEnvironment` as it is. When the environment stops needing the
  key, its rows and vault entry are deleted.

### Control: the relay

- Row `mail-relay`: `s.protocol('POST', '/platform/mail/*')`. Bun process only; the Worker answers 404.
- Authentication: the bearer is an application key (hash lookup, unexpired → `<app>@<env>`) or the installation key
  of IAM: `HMAC-SHA256(FABRIKA_IAM_RPC_KEY, 'fabrika-platform-mail')` as `px_` + hex, compared in constant time. An
  installation sender is recorded as `installation:iam`.
- Idempotency: `UNIQUE (sender, idempotency_key)`; the fingerprint is SHA-256 of the canonical request body. A repeat
  with the same fingerprint answers the first `messageId`; a different one is `idempotency_conflict`.
- The gate, decided once at acceptance:
  - an installation sender: `queued`, always;
  - Control has no transport (`MAIL_TRANSPORT` none or invalid): `held`;
  - otherwise the most specific rule: scope `<app>@<env>` with the exact recipient domain, then that scope with `*`,
    then scope `*` with the exact domain, then `*`/`*`; no rule: `pass`. `pass` → `queued`, `hold` → `held`,
    `drop` → `dropped`. The rule's id is recorded on the message.
- States: `held`, `queued`, `sent`, `failed` (not sent, final), `unknown` (may have left, final, for a person),
  `dropped`. `released` is `held` → `queued` by an operator.
- Dispatch: a `PostgresJobQueue` queue `vozka-mail`, one job per queued message, consumed by the Control server
  beside `vozka-deploy`. The consumer sends through the installation `EmailSender` (`emailSenderFromEnv` of Control's
  own `FABRIKA_EMAIL_*`) under the row's key prefixed `relay:`, with a 30 s deadline. Outcome: `sent`; a retryable
  error that `mayRetryDelivery` allows → requeued with backoff (1 min doubling, at most 5 attempts) → then `failed` or
  `unknown` by its outcome; any other error → `failed` or `unknown` by its outcome. `runMaintenance` re-enqueues
  `queued` rows older than 10 minutes and purges content (`content = NULL`) of final rows: at once for an
  installation sender after `sent`, after 30 days for every other final row.

### Control: tables (migration `0013_mail_relay.sql`, both dialects)

- `platform_transport_keys(app_id, env, receiver, key_id, key_hash UNIQUE, value_ref, expires_at, created_at)`,
  PK `(app_id, env, receiver, key_id)`, FK `(app_id, env)` → `app_envs` ON DELETE CASCADE.
- `mail_messages(id PK, sender, idempotency_key, fingerprint, recipient_domain, state, rule_id NULL, decided_by NULL,
  attempts, next_attempt_at NULL, provider_message_id NULL, error_code NULL, content NULL (JSON text of the request
  body), created_at, updated_at)`, `UNIQUE (sender, idempotency_key)`, index `(state, next_attempt_at)`.
  `recipient`, `subject` and the bodies live only in `content`.
- `mail_rules(id PK, scope, domain, action, created_at, updated_at)`, `UNIQUE (scope, domain)`; `scope` is `*` or
  `<app>@<env>`, `domain` is `*` or a lowercase domain, `action` is `pass | hold | drop`.

### Control: console

- Actions: `mail.read` (list and metadata, scoped by app/environment for app senders, global for installation
  senders), `mail.content.read` (recipient, subject, bodies; global), `mail.manage` (release, drop, rules; global).
  Added to `controlSchema.actions`; only `admin` (`*`) holds them by default.
- RPC: `mail.messages.list({ state?, scope?, cursor? })`, `mail.messages.get({ id })` (content only with
  `mail.content.read`), `mail.messages.release({ id })`, `mail.messages.drop({ id })`, `mail.rules.list()`,
  `mail.rules.set({ scope, domain, action })`, `mail.rules.remove({ id })`. Release and drop act on `held` only.
- Dashboard: a Delivery page "Mail" (list by state, detail with content when allowed, release/drop with a confirm),
  and a rules section.

### IAM

- On Zerops, when IAM has an email provider configured and `FABRIKA_CONTROL_URL` is set, its sender is a
  `PlatformEmailSender` to `<FABRIKA_CONTROL_URL>` with the derived installation key; otherwise today's sender. Its
  manual action-link flow (no provider) is unchanged.
- `FABRIKA_CONTROL_URL: http://control:3000` joins IAM's Zerops setup (regenerated `zerops.yaml`).
