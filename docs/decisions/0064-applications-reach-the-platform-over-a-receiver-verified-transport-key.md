# 0064 — Applications reach the platform over a transport key that the receiver verifies

## Context

An application reaches installation services over several channels. Each one added its own transport, its own
credential and its own retry rule:

- **Membership.** The application calls IAM with `FABRIKA_IAM_RPC_KEY`, a key pinned to its `<app>@<env>`. IAM
  serves the call on a `protocol` row and verifies the key itself. Control issues the key, keeps its hash, and seals
  and rotates the value ([ADR-0022](0022-the-proxy-is-the-only-enforcement-point.md)).
- **Connectors.** The application holds a key of the `app` principal kind. The owner's proxy exchanges it at IAM, and
  the endpoint table decides (ADR-0022).
- **Mail.** An application whose job declares `mailer: 'installation'` received the installation's provider
  credential and sent directly ([ADR-0019](0019-portable-outbound-email.md) §4). The platform could not record,
  queue, hold or drop that mail. An operator could not hold back a new application while reading what it sends, and
  a local stack could only capture mail to a directory.

Mail is the only channel that handed a platform secret to the application. Moving mail into Control needs a way for an
application to call an installation service that:

- reaches one receiver, as one application environment, and nothing else;
- is issued and revoked by Control, which already deploys the application;
- survives `fabrika platform upgrade` without a re-issue;
- lets the caller retry a lost answer without a second effect;
- is additive, so an application on an older framework release keeps working unchanged
  ([ADR-0062](0062-a-platform-release-serves-older-framework-releases.md)).

## Decision

**An application calls a platform receiver with a key per application environment and receiver. Control issues,
hashes, seals and rotates the key; the receiver verifies it on a `protocol` row and records each call under the
caller's idempotency key. Mail is the first receiver.**

### 1. Receivers and variables

- A receiver is a named platform service an application calls. The receivers are a closed list in `@fabrika/auth-core`
  (`PLATFORM_RECEIVERS`); today it holds `mail` only.
- Each receiver has two variables, `FABRIKA_PLATFORM_<RECEIVER>_URL` and `FABRIKA_PLATFORM_<RECEIVER>_KEY`
  (`platformTransportVariables`). `FABRIKA_PLATFORM_` is a framework-only family (`FRAMEWORK_VARIABLE_PREFIXES`), so
  no application sets a variable under it, and a deploy removes one it no longer hands.
- The URL is an http(s) origin and public: the error-report scrubber of
  [ADR-0059](0059-application-server-errors-carry-their-stack-and-message.md) keeps it. The key is a secret.
- Control derives the receivers from the approved artifact. A job with `mailer: 'installation'` uses the `mail`
  receiver. Nothing new is declared, and the approval shows what it showed before.

### 2. The key

- One key per `<app>@<env>` and receiver: `px_` and 160 random bits, generated by Control.
- Control stores only its SHA-256 hash, in `platform_transport_keys`. It seals the value in the vault under
  `platform:platform-key:<app>@<env>:<receiver>`, to hand it to the next deploy. It never logs the value and never
  returns it over the API.
- A key lives 30 days. A deploy reuses the newest key while more than half of its life is left, and issues a new one
  otherwise. A replaced key stays valid by its hash until its own expiry, so a running version keeps working; Control
  never hands its value out again.
- When an environment stops needing a receiver, the deploy that drops it deletes the receiver's keys and their vault
  entries once it succeeds: when the provider's deploy, its reconcile or a cancellation settles the run succeeded. Until
  then the previous version runs and calls the receiver with its key. A failed, interrupted or dry run deletes nothing.
  The membership key follows the same moment: IAM deletes it with the schema reconcile of the version that went live.
  Deleting the application environment deletes its keys (`ON DELETE CASCADE`).
- A Control without a vault (`FABRIKA_CONTROL_VAULT_KEY`) cannot issue a key, so it refuses a deploy that needs one.
  A dry run issues no key.

### 3. Admission

- The receiver serves one `protocol` row per transport. The proxy makes no enforcement decision for it (ADR-0022).
  The receiver authenticates the bearer and authorizes on the key's application environment, never on a body field.
- The receiver hashes the bearer and looks up an unexpired row of its own receiver. A key of another receiver, an
  expired key and an unknown key are all refused alike.
- An installation service has no application environment. It authenticates with a key derived from a secret it
  already shares with Control. IAM's key is `px_` and the hex of `HMAC-SHA256(FABRIKA_IAM_RPC_KEY,
  'fabrika-platform-mail')` (`installationMailKey`). The receiver compares it in constant time and records the caller
  as `installation:iam`.
- An application's URL is Control's public origin (`FABRIKA_CONTROL_DOMAIN`), as its membership transport's is IAM's
  public origin. An application namespace is a Zerops project of its own, and projects share no private network
  ([ADR-0014](0014-provider-owned-deployment-namespaces.md)). The platform proxy serves the receiver's `protocol` row
  on that host and passes the bearer through. A Control without a public origin refuses a deploy that needs the
  receiver.
- IAM runs in the installation's project and calls Control's private origin, `http://control:3000`.

### 4. The receiver's idempotency contract

- Every request carries the caller's idempotency key. The receiver records `(sender, idempotency key)` with the
  fingerprint of the request, the SHA-256 of its canonical body, before it answers.
- A repeat with the same fingerprint answers the first result and has no second effect. A different fingerprint
  under the same key is `idempotency_conflict`.
- The caller can therefore treat the receiver as idempotent whatever the receiver does downstream. Its retry rule is
  the receiver's general one; for mail it is `mayRetryDelivery` over `idempotent: true`.
- Both sides import one wire module (`@fabrika/email/platform` for mail). It holds the encoding, the one parser of a
  request, and the status of each answer. The parser is strict: a field the release does not know is refused, never
  dropped.

### 5. Which deploys get it

- Zerops only, on the namespace-proxy path. On Cloudflare a deploy refuses every `FABRIKA_PLATFORM_*` variable, as it
  refuses `FABRIKA_EMAIL_*`: Cloudflare runs no job.
- Only an application whose approved snapshot records framework release 0.7.0 or newer gets the platform transport. A
  prerelease compares as its release.
- An older release, and a snapshot that records no framework release, keeps what it had: for mail, the installation's
  `FABRIKA_EMAIL_*` with the provider credential. The platform transport is additive under ADR-0062.
- Zerops writes the URL as a plain service variable and the key as a sensitive one.

### 6. The mail receiver

The wire is `POST <FABRIKA_PLATFORM_MAIL_URL>/platform/mail/send` with `Authorization: Bearer <key>` and a JSON body
of the `EmailMessage` fields, attachments as base64. The answer is `200 { status: 'accepted', messageId }`, or an
`EmailDeliveryErrorCode` with its status, so the receiver's `retryable` and `outcome` reach the caller unchanged.
What the relay does with the message, its gate and its dispatcher, is [ADR-0019](0019-portable-outbound-email.md) §8.

## Consequences

- An application on framework 0.7 holds no provider credential. Its key reaches one receiver, as one application
  environment, and Control revokes it when a deploy that no longer needs it succeeds.
- Adding a receiver is a name in `PLATFORM_RECEIVERS`, a `protocol` row on the receiver and a key reconcile in the
  deploy. It needs no new variable family and no change in IAM or the proxy. Membership, audit and job reports may
  move onto it later; each is its own decision.
- The receiver is a dependency of every call. While Control is unreachable, a relayed send fails
  `provider_unavailable` (retryable, outcome `unknown`), and the application retries it, because the receiver is
  idempotent.
- A deploy of a 0.7 application with a mailer job needs Control's vault. An installation without one cannot deploy it.
- A deploy that issues a key also deletes every expired key row of the installation. It deletes only its own
  environment's vault values, so other environments' expired values stay in the vault
  ([backlog 194](../backlog/194-mail-relay-follow-ups.md)).
- During the ADR-0062 window, an installation has two kinds of mailer applications: those on the relay and older ones
  that still hold the provider credential. The gate covers only the first kind.

**Rollout of an existing installation:**

1. **Generated files.** The transport changes no installation file. Control's console table gains the `mail-relay`
   row, so `platform deploy` rewrites `FABRIKA_SERVICE_TABLE_DIGEST` with the regenerated manifest. IAM's setup in
   the release's generated `zerops.yaml` gains `FABRIKA_CONTROL_URL`; the sidecar builds IAM from the tag's checkout,
   so `platform upgrade` carries it.
2. **Environment variables.** An existing application environment converges at its next deploy. A 0.7 release gets
   `FABRIKA_EMAIL_PROVIDER=platform` and the `FABRIKA_PLATFORM_MAIL_*` pair, and the deploy removes the provider's
   variables, which it no longer hands. The key is sensitive and cannot be read back, so every deploy writes it.
   An older release keeps its `FABRIKA_EMAIL_*`.
3. **Provider state.** Migration `0013_mail_relay.sql` only adds tables. The dispatch queue `vozka-mail` lives in the
   existing jobs table. No resource an older version created is checked again.
4. **Floating pins.** None. The choice reads the framework release recorded in the approved snapshot, not a pin that
   floats. A snapshot recorded before Control recorded the release reads as an older application.

## Alternatives considered

### An `app` workload key at IAM, through the proxy

The connector wire: the application holds a key of the `app` kind, the proxy exchanges it at IAM, and the endpoint
table decides. It would reuse ADR-0022's one enforcement decision. Rejected because Control's own IAM schema is
static, and its reconcile replaces the whole vocabulary on every platform upgrade. A workload per application in that
schema would be revoked on every upgrade, and each application's mail would stop until its next deploy.

### The job's workload token as the bearer

A job already holds a token that IAM signs. Rejected because that token's audience is the application. Presenting it to
Control uses a token outside its audience: any service that accepts it turns every token the application sees into a
credential at that service. A transport key names its receiver and nothing else.

### Keep the provider credential in the application

What framework 0.6 and older do. Rejected for new releases because the platform then has no record and no gate. It cannot
hold a new application's mail, drop mail to a domain, or show an operator what left. The credential also spreads to
every application that sends.
