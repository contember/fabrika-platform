# 71 — Deliver domain audit events durably

**Summary.** Give every state-changing operation of Control and Operations a transactional, retryable and
idempotent path to the IAM audit log, through an outbox. IAM's own changes already write their audit rows in
their own transaction (the paved-road sprint, WU18). Effort L.

## Problem

`IamRpc.audit` is intentionally fire-and-forget. The IAM implementation registers the write with the
runtime, returns success before persistence and logs rather than propagates a storage failure. Callers
therefore cannot tell whether an audit event became durable. Moving a current `auth.audit(...)` call
before a mutation can record an operation that never committed; leaving it after the mutation can lose
the event in the crash window. Blind caller retry can create duplicates because the audit API has no
stable event identity or idempotent acknowledgement.

This applies to the domain mutations of Control and Operations. The authenticated Zerops source-connection
flow follows the same established audit semantics as the other Control mutations. Its setup state,
authorization and secret durability remain valid; this item does not make that feature privately
blocked or justify a one-off audit mechanism inside it.

IAM's own mutations are out of this item: membership, links, grants, roles, principals, credentials and
sessions write their `audit_events` row in the change's batch, and logins and logouts write `auth_log` before
the answer (`packages/iam/CLAUDE.md`). Application audit stays in application tables, in the invocation's
transaction; there is no framework audit API for applications.

The request correlation value (`request_id`) is a different thing: IAM bounds it and its composition
roots name where it may come from (`packages/iam/src/request-id.ts`). This item concerns durable,
exactly-once-visible delivery of a domain event and needs a separate stable event id.

## Approach / acceptance

- Define a stable domain audit event id generated by the mutation producer and accepted by IAM.
- Make the IAM write idempotent under that id and return only after the durable insert or an exact
  duplicate is confirmed.
- In Control and Operations, persist the mutation and a redacted audit outbox record in one local database
  transaction. Do not create a fake global transaction across services.
- Dispatch the outbox with bounded retry. Delete or mark an entry delivered only after IAM's durable
  idempotent acknowledgement. A crash before acknowledgement may resend the same event id and must not
  create another visible audit row.
- Keep credentials, tokens, callback codes, opaque states and secret values out of outbox payloads, logs and
  error envelopes.

Acceptance needs fault-injection tests for a crash after the domain commit, after IAM persistence and
before producer acknowledgement, plus concurrent duplicate delivery. Each committed mutation must
eventually have one audit row, an uncommitted mutation must have none, later events must continue past a
failing entry, and retry diagnostics must remain redacted. Both SQLite/D1 and Postgres compositions must
exercise their real transactional and concurrency behavior.

## Touch points

`packages/auth`, `packages/iam` (the idempotent `audit` write only), `packages/control`, `packages/operations`,
their contract packages, runtime schedulers and SQLite/Postgres migrations; mutation-focused tests in Control and
Operations.
